# liklo — B站直播录像 → 音频 → 语音识别 → 内容报告

一个零依赖（只用 Node 内置模块）的本地流水线：

```
UP 主页 / 录播链接
      │
      ▼
  1. yt-dlp 只下载音频  (-f ba)
      │
      ▼
  2. 文件名 = 当前日期 + 主播英文名（无空格/特殊字符）
      │
      ▼
  3. 多P 视频默认只下载第 1P（可单独开启「全部P」；多P 会用 ffmpeg 拼接），切分成 ≤5 分钟片段（`MAX_SEGMENT_SECONDS`），逐段（严格串行）送 ASR，
     再把时间轴偏移修正后合并成完整转录
      │
      ▼
  4. 本地 LLM 生成报告：直播内容概括 / 亮点名场面(带起始时间戳) / 辛辣锐评
      （锐评不是客观评价，而是风趣幽默、带戏剧性的吐槽：只调侃这场直播里的「梗」和名场面 —— 玩梗、
      整活、口嗨、黄段子、嘴硬、破防、翻车；对离谱之处直接说「太变态了」，对暖心之处直接说「太感动了」。
      不人身攻击、不刻薄、不评价主播的性格/人品/能力，依据均来自转录）
      │
      ▼
  5. 网页展示（时间戳可点击，跳转到原视频对应位置）
```

## 运行

```bat
start.bat
```

或手动：

```powershell
node src/server.js
```

然后打开 <http://localhost:3200>。

> 需要 Node 22+（`node:sqlite`）。`runtime/` 里可以放 `yt-dlp.exe`、`ffmpeg.exe`、`ffprobe.exe`，
> 也可以用 `LIKLO_YTDLP` / `LIKLO_FFMPEG` / `LIKLO_FFPROBE` 指向系统安装（仓库不包含这些二进制）。

## 使用

1. **添加主播**：粘贴 UP 主页链接（如 `https://space.bilibili.com/1290874/upload/video`）或直接填 mid。
   系统解析出 mid 与主播名，并从名字/标题中推导出英文名（如 `莉蔻Liko` → `liko`）用于命名文件。
2. **开启监控**：打开「监控」开关，每 10 分钟检查该 UP 的最新上传，只有标题命中关键词
   （默认 `录播,直播,录像`，可自定义）才自动入队，且同一 bvid 不会重复处理。
3. **只抓指定主播**：一个 UP 频道可能有多位 VTuber（例如「牧场草原神official」下有莉蔻Liko /
   枝堇Sumire / 命依Mei）。在「标题必须包含」里填 `莉蔻,Liko`，只有标题含其中任一词的录播才会入队
   （留空则不限制）。文件名用的英文名也从标题推导（`莉蔻Liko 旅游第一天` → `liko`），比 UP 显示名更准。
4. **手动提交**：粘贴任意录播链接（`https://www.bilibili.com/video/BVxxxx`）立即执行。
5. 任务列表显示阶段（下载 → 切分 → 逐段转写 `i/n` → 生成报告），完成后渲染报告，
   `HH:MM:SS` 自动变成 `?t=<秒>` 链接，点击即跳转到原视频该时间点。完整转录可展开查看。
6. **取消任务**：排队中或处理中的任务可以点「取消」，正在运行的 yt-dlp / ASR / LLM 请求会被中止；
   已完成的 ASR 片段缓存保留，之后点「重试」不会重新转写已完成的片段。
7. **报告库**：`http://localhost:3200/reports` 是独立的报告页面，列出所有已完成（`status=done`）的报告，
   可按标题/主播/关键词搜索、按最新生成 / 最早生成 / 时长排序；报告正文默认折叠（点开才渲染），
   每条都有「下载 Markdown」「复制报告」，以及「带时间戳的转录」——点开就在同一页内展开时间轴
    （可过滤内容/说话人、点击时间戳跳转到原视频对应位置），不需要切回任务列表。
    「姓名修正」按当前姓名表重新调用大模型校验人名（改姓名表后点它即可撤销或补上修正）；
    「重新生成报告」不下载、不转写，只用已有转录 + 姓名修正重新调用大模型生成一份新报告
    （任务页也有同一个按钮）。
   任务列表里的「重新转录」删除该任务的转录结果和 ASR 缓存，用「服务配置」里当前设置的 ASR
   重新转写（已下载的音频与切分片段保留），然后重新生成报告并姓名修正 —— 换 ASR 服务或模型后
   用它重跑最省事。
8. **公开只读报告页**：`http://localhost:3210`（独立端口，监听 `0.0.0.0`，可转发到互联网给其他人看）。
   只有「浏览 / 搜索 / 按主播过滤 / 展开报告 / 下载 Markdown / 带时间戳的转录 / 分享链接」，
   没有任何添加、监控、取消、删除、重试等编辑或任务管理功能。每条报告都有直链 `/r/BVxxxx`，
   打开即直接展开该报告，适合直接发给别人。

## 长直播的报告生成（分段模式）

几小时的录播（转录 10 万字左右）不可能一次生成完整报告，所以 `src/report.js` 分两步走：

1. **上下文窗口自动检测**：`llmContext()` 读 LLM 的 `/props`（`n_ctx`），`config.LLM_MAX_CONTEXT` 只是手动覆盖；
   检测失败时回退 16384。
2. **校准过的 token 估算**：按字符类别估算（CJK 0.75 / 数字 1.5 / 其他 0.4 token/字符），
   对真实转录的误差约 3%，且总是高估（避免把 86k token 的提示塞进 60k 窗口）。
3. **短转录（≤30000 估算 token）**：单次生成，输出目标随转录长度增长
   （`3000 + 输入 token × 0.12`，不超过窗口允许的上值），若模型因 `max_tokens` 截断则自动续写
   （最多 3 次，续写条件按 token 判断而不是字符数 —— 之前用字符数比较 token 预算，中文
   1 token ≈ 1.3 字符，条件永远成立，续写从未触发，所以报告经常停在半句）。
   生成后 `completeReport()` 再做一次确定性的完整性检查：按标题拆出三个章节，缺失的章节
   （模型只写了两段就结束）单独补生成；总结部分如果没有覆盖到转录的最后时间（没有时间戳
   时视为只写到半场），只送后半段转录再补一段按时间顺序的总结。实测旧报告里
   `BV1qXJQ64EA6`、`BV1teJY6oEng`、`BV1gaJ26iEfz` 这类单次生成的报告总结只覆盖到直播中间，
   分段模式生成的报告（`BV1Jtpj6BEVh` 等）则不需要补。
4. **长转录（>30000 token）：分段模式**
   - 转录按 12000 token 切块，每块一次「记录要点」调用（`reasoning_effort: none`，快），
     输出该段时间的 chronological 摘要 + 机器可读的 `【名场面】` / `【有梗场面】` 列表；
   - 报告正文由代码拼装：概览 + 「一、直播内容详细总结」（每块一段，带时间区间）
     + 「二、精彩亮点 / 名场面」（一次调用整理去重后的候选）
     + 「三、辛辣锐评」（只评场面，不评人，每 8 条一组分多次调用，前几组用过的模板句会被禁止）；
   - 锐评只送 24 条（按时间均匀分布，覆盖整场），每条允许两句，句式要求变化 ——
     送 50 条时模型会写成一行一条的模板化清单。
5. **输出清洗**：`cleanDegenerate()` 折叠「不能。不能。不能。」这类退化重复，
   `trimIncompleteEnd()` 删掉被输出上限截断的半行，`normalizeHeadings()` / `stripTitleEcho()`
   去掉模型自己加的标题，保证页面上只有三个 `##` 章节；`cleanStutter()` 处理「不是「别炫耀」
   而是「别炫耀不是「别炫耀」而是…」」这种同一引语写两遍的自我复制（引语后再分析是正常写法，
   中间有标点或逗号时不会动）。
6. **句式重复兜底**：`templateCounts()` / `worstReuse()` 统计「比任何…都更…」「太X了」
   这类模板句，`repeatedPhrases()` 更通用 —— 任何连续出现 ≥6 次的中文短语都算模板
   （模型被禁止一个句式后会换一个新的，所以不能只列已知句式）。`diversify()` 一旦发现
   就重新生成一次，提示里明确禁止这些句子，并保留重复更少的那一稿；出现在提示原文里的
   短语（人名、转录引语）不算模板，不会被禁止。提示里不点名句式：实测「如「太变态了」「比任何…都更…」最多用两次」这类例句会让模型更频繁套用它们（同一批 8 条场面，点名式提示模板句 0/4/8 次，只描述写法「先复述场面并引用原话，再一句补刀，相邻两条句式不能相同」的提示 0/0/0 次），所以例句只出现在代码里的检测规则中，被禁止的句子只在检测到重复之后追加。阈值刻意设得较松（单段 ≥6 次才重试，跨组累计 ≥5 次才禁止，最多重试一次）：设成 4 时几乎每段都要重试，既慢又没有明显收益。
7. **重试的内容不会被丢弃**（`mergeDrafts()`）：重试是同一素材的第二稿，以前只保留重复更少的那一稿，
   另一稿里模型提到的场面就丢了（模型两次不会覆盖同一批场面）。现在按时间戳合并：把保留稿里没有的
   条目按时间顺序插入（自己套用被禁止句式的条目不插入），概览这类没有时间戳的段落不合并。
   其他重试路径同样保证不丢内容：整组锐评失败时拆成 4 条一组逐组生成（不是只保留前 4 条），
   某个块失败时拆成两半（成功的半块保留），续写内容追加到已写内容之后（若模型从头重写而不是续写，
   则停止而不是重复拼接），姓名修正的候选批次失败时拆成两半重试（所有候选都会被确认，而不是只确认前 4 个）。

8. **拼装收尾（`assembleReport()`）**：模型输出的结构不可靠（同一个 `## 二` 标题出现两次、
   名场面条目混进总结章节、编号从草稿继承变成 1,2,3,6,10,11、同一时间戳的同一场面写成两种格式）。
   所以两条生成路径的最后都跑一次确定性的拼装：按标题重新切分，每个块按内容形状归类
   （`【名场面】` 类列表 → 亮点，带时间区间的粗体标题 → 总结，带时间戳的评论 → 锐评），
   同一时间戳且内容互相包含的条目合并，章节内按时间排序，亮点和锐评重新编号为
   `**N. [HH:MM:SS] 标题**`，总结里时间区间重叠的相邻块合并，段落内「把一次 X 写成一种 Y」
   这类同义反复的从句只保留一个。`BV163nE6gE9v` 的旧报告离线跑：14950 字符 / 239 行 /
   5 个标题 / 4 条编号条目 → 10065 字符 / 166 行 / 正好 3 个标题 / 42 条编号条目，合并 22 个
   重复场面、6 个重叠的总结块。

9. **静默段**：ASR 对没人说话的时段会输出 `[音乐]`、`[S01]`、`嗯` 这类占位行，转录里
   因此有大量无内容行。`src/transcribe.js:buildTimeline()` 只送有真实内容的行
   （`hasSpeech()`：去掉占位符、重音符号和 `music/bgm/数字/音乐` 这类 token 后还剩 ≥2 个
   字符），把 ≥60 秒的空档合并成一条 `[静默段 HH:MM 至 HH:MM 无人说话]`；开播到第一条
   转录之间同样算一段（ASR 没有输出就是没有说话）。提示里说明这段时间确实没人说话：可以
   提一句「开播前有一段静默」，但不要编造事件，每个环节的时间区间从该环节第一段真实说话
   开始。生成之后 `anchorOpening()` 用转录的第一条真实说话核对第一个章节的时间区间（纯
   确定性，不调模型，重复运行结果不变）：区间完全落在静默段内 → 改成 00:00 → 第一条说话；
   区间跨过第一条说话 → 起点改为第一条说话。`public/common.js:renderTimeline()` 用同一规则
   把空档显示成一行「静默 …（无人说话）」，管理页、公开页和静态导出共用。实测 101 条转录：
   提示 token 5,410,622 → 5,218,038（省 3.6%），要点调用 500 → 485，51 条转录的开场静默被
   标记出来；库里 100 条报告的首个章节区间全部校验通过。

实测（三段转录，离线跑 `src/report.js`）：

| 转录 | 估算输入 | 报告 | 耗时 | 结果 |
| --- | --- | --- | --- | --- |
| `BV1Jtpj6BEVh` 105777 字符（4 小时） | 89k token / 8 块 | 14024 字符 | 222 s | 三段齐全，锐评 24 条分 3 组生成，一组触发一次重试，整段最高重复 4 次 |
| `BV1qMpm6QEsV` 93120 字符 | 79k token / 7 块 | 11860 字符 | 186 s | 三段齐全，锐评 24 条，零句式重试，结尾完整 |
| `BV1ijWA6aEEd` 68562 字符 | 58k token / 5 块 | 9443 字符 | 172 s | 三段齐全，锐评 23 条每条 100 字左右，`worstReuse` 0（「比任何…都更…」只出现 3 次），零重试 |

## 姓名修正（人名纠错）

`src/names.js` 分两步，确定性扫描 + 有界的大模型确认：

1. **扫描覆盖整段转录**：报告正文 + 转录全文都参与扫描（以前只扫前 80000 字符，
   4 小时录播的后半段完全没被看过，只在最后一小时出现的人名永远查不出来）。
   扫描本身很便宜：离线跑三段最长的转录（10 万 / 16 万字）约 0.2–0.35 秒。
   为了在全文扫描下仍然快，只枚举可能长度（已知写法长度 ±2）的窗口，并且先做
   「字符集合」预筛 —— 一个候选要么含该名字的字，要么每个字都是同音替换，
   否则不可能在编辑距离 2 之内，直接跳过。
2. **候选数量随转录长度增长**：上限 `20 + 每 2 万字 4 个`，封顶 60。4 小时的录播
   人名和错写比 1 小时的多，固定 20 个会把尾部候选挤掉；每 8 个候选一批送大模型确认，
   失败的批次拆成两半重试一次（所有候选都会被确认）。
3. **确认调用有界**：这类调用用 `reasoning_effort: none`、`max_tokens 1500`、
   `NAME_CALL_TIMEOUT_MS`（默认 90 秒）。之前用默认推理 + 4000 token：模型思考占满补全
   预算，JSON 返回为空，批次失败后拆半重试，一段 4 小时录播能调用几十次，任务看起来
   卡在「姓名扫描」然后报「生成失败」。整个阶段还有 `NAME_TIME_BUDGET_MS`（默认 3 分钟）
   的总时限，超时后剩余候选跳过并记日志。
4. 大模型只负责判断「这是人名还是普通词」，替换由代码做（字符串替换），所以报告和
   转录不会被模型改写；`correct` 必须能解析到姓名表条目，否则该修正被丢弃。
   已记录的修正若姓名表仍然支持就保留，只撤销不再支持的（改表后点「姓名修正」即可）。
   姓名修正失败不影响报告本身：失败时只记日志，报告照常保存。

日志会打印 `[names] job N: scanned <字符数> candidates <数量> (cap …)` 和
`[names] confirmed <数量> name fixes from <数量> candidates`，方便确认扫描范围与耗时。

## 队列、取消、删除与断点续跑

- 任务在内存队列中**严格串行**执行（ASR 不能并发），监控自动发现的新录播也走同一队列。
- 每个运行中的任务都有一个 `AbortController`；取消时队列里排队的任务直接移除，正在执行的任务
  中止其子进程与 HTTP 请求，状态置为 `cancelled`。
- **删除任务**（列表里的「删除」按钮，或 `DELETE /api/jobs/:id`）：从队列移除、中止正在执行的
  下载/转写/报告，删除数据库行，并清理切分片段（`.segNN.*`、`.concat.txt`）。默认**保留**已下载的
  音频、`data/transcript-<bvid>.json` 和 `data/asr-cache/<bvid>/`，这样同一条录播以后重新提交时
  不用重新下载或重新转写；加 `?purge=1`（网页里确认对话框选「确定」）则连这些一起删掉。
  想验证这段逻辑而不跑网络：`node scripts/test-delete.js`（自建两个临时任务与假文件，检查删什么、留什么）。
- 进程重启时，状态为 `running`/`pending` 的任务会被重新入队；已下载好的音频会被复用
  （用 ffprobe 校验时长，截断的音频会重新下载）。
- **转录结果按 bvid 缓存**：ASR 片段结果存 `data/asr-cache/<bvid>/segNN_<时长>s.json`（文件名带片段时长，
  片段长度变化时旧缓存自动失效），全部片段完成后
  合并写入 `data/transcript-<bvid>.json`（时间轴已按片段偏移修正）。同一 bvid 再次运行时直接
  复用转录，只有报告阶段重新执行 —— 调试报告提示词时不必重新转写。
- 只改报告提示词时可以用 `POST /api/jobs/:id/report` 或 `node scripts/report-only.js <jobId|bvid>`。

## 清理残留文件（重启测试前）

`scripts/cleanup.js` 删除**中途终止**的任务（状态为 `cancelled` / `error` / `pending`）产生的切分片段，
并把这些任务的阶段重置为 `queued`；正在运行的任务不会被动。转录与 ASR 缓存**默认保留**（它们是完整
结果，后续运行会复用），只有 `--purge-cache` 才删除。

```powershell
node scripts/cleanup.js --dry-run      # 先看要删什么
node scripts/cleanup.js                # 删除中断任务的切分片段
node scripts/cleanup.js --all          # 也删除已完成任务的切分片段
node scripts/cleanup.js --purge-cache  # 同时删除 transcript 与 data/asr-cache（彻底重新转写）
node scripts/cleanup.js --keep-audio   # 保留已下载的音频，只删切分片段
```

## ASR 服务

**当前默认：`http://192.168.1.126:8000/v1`**（与本地 LLM 同一台机器，`MOSS-Transcribe-Diarize-q5`，
16 核 / 16 线程）。它是 FastAPI 风格的服务：`GET /health`、`GET /v1/models`、
`POST /v1/audio/transcriptions`（`multipart: file`，也接受 `audio_url` / `audio_path`），返回
`{text, segments:[{start,end,speaker,text}], audio_duration, rtf}`，与 liklo 的 `verbose_json` 解析兼容；
`model` 字段被忽略，所以界面里的模型名只是显示用。实测 300 秒片段 RTF ≈ 1.05，比下面的 `.144`（RTF ≈ 2.1）快一倍。
该服务没有 `/healthz`，也没有队列状态字段，所以「服务状态」检测会依次尝试 `/healthz` 和 `/health`。

**这个服务直接接受 `.m4a`**（旧版本只接受 WAV，送 `.m4a` 会返回 `500`）。liklo 直接送切分出来的
m4a 片段；只有当上传返回 400/415/422/500 时才退回到 ffmpeg 转 16 kHz 单声道 PCM WAV
（临时文件 `<片段>.asr.wav`，请求结束后删除）再重试一次，所以换一个只读 WAV 的服务也不用改配置。

下面是旧部署（`192.168.1.144`）的记录，仍然可用，把 `ASR_BASE` 改回
`http://192.168.1.144:8100/v1` 即可。旧的 ASR 服务（`192.168.1.141:8100`，LocalAI 包装）任何转写请求都不返回，所以重新在
`192.168.1.144`（Alpine，12 核 / 16 GB，QEMU 虚拟机）上部署 [moss-transcribe.cpp](https://github.com/localai-org/moss-transcribe.cpp)：

```sh
# 依赖
apk add --no-cache curl git cmake gcc g++ make ffmpeg nodejs
# 编译
git clone --recursive https://github.com/localai-org/moss-transcribe.cpp
cd moss-transcribe.cpp && sed -i '3i #include <cstdint>' src/config.hpp   # 上游缺少 include
cmake -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j12
# 模型（q5_0：618 MB，比 f16 快约 2 倍，转录结果与 q5_k 一致）
curl -L -o /root/models/moss-transcribe-q5_0.gguf \
  https://huggingface.co/mudler/moss-transcribe.cpp-gguf/resolve/main/moss-transcribe-q5_0.gguf
```

命令行用法（只读 WAV）：

```sh
MTD_THREADS=12 ./build/moss-transcribe transcribe /root/models/moss-transcribe-q5_0.gguf audio.wav --format json
```

`--format json` 输出的是裸数组 `[{id,start,end,speaker,text}]`，时间相对于送进去的音频。

`/root/moss-api/moss-api.js` 是一个零依赖的 Node HTTP 包装，暴露
`POST /v1/audio/transcriptions`（`multipart: file` + `model` + `response_format=verbose_json|json|text|srt`）、
`GET /v1/models`、`GET /healthz`，请求严格串行处理；非 WAV 音频由服务端 ffmpeg 转成 16 kHz 单声道 WAV，
所以客户端仍然直接送 `.m4a` 片段。用 OpenRC 管理（开机自启）：

```sh
# /etc/init.d/moss-api 必须是 #!/sbin/openrc-run，并且显式 --background（否则 rc-service 会挂住）
rc-update add moss-api default
rc-service moss-api start      # 监听 0.0.0.0:8100，局域网可访问
rc-service moss-api status
tail -f /var/log/moss-api.log
```

### 实测速度（192.168.1.144，i5-13500H / 12 线程 / AVX2）

| 项目 | 实测 |
| --- | --- |
| 模型加载（每个请求都要重新加载一次） | ~7 s |
| 60 秒音频（含加载） | 39 s |
| 300 秒片段（含加载） | 620 s ≈ 10.3 分钟（RTF ≈ 2.1） |
| 61 分钟录播（13 段） | 约 2.2 小时 |

同一模型、同一数据，换机器前（`QEMU Virtual CPU version 2.5+`，只有 SSE4.2，无 AVX/AVX2）的
数字是：模型加载 ~45 s，60 秒音频 211 s，300 秒片段 1229 s，61 分钟录播约 4.4 小时。
**AVX2 让整体速度提升约 2 倍**（模型加载快 6 倍）。`CMakeLists.txt` 里 `GGML_NATIVE ON`
即 `-march=native`，所以换 CPU 后必须重新 `cmake --build build` 才能用上新指令集。

RTF 随片段长度上升（60 s → 0.5，300 s → 2.1，注意力是二次的），所以更短的片段总耗时略低，
但说话人分离（diarization）的上下文会变差。5 分钟是速度与质量折中的默认值，可用
`MAX_SEGMENT_SECONDS` 调整。

## 已知问题与处理

- B站部分接口（space / dynamic / user-info）返回 404 或 412 限流，因此主播视频列表用
  yt-dlp 的 `space.bilibili.com/<mid>/upload/video` 抓取，标题与时长用 `web-interface/view` 逐个查询，
  并内置退避重试。
- ASR 服务较慢，切分片段严格串行请求，不能并发。
- **moss 后台报 `code=canceled`**：服务端把请求取消，通常是因为**客户端先断开了连接**（超时、进程被 kill）。
  模型首次请求需要加载，耗时远超过普通请求；客户端提前断开后服务端每次都要重新加载，于是永远出不来结果。
  因此第一个请求要耐心等待（`ASR_TIMEOUT_MS` 默认 40 分钟），不要中途 kill 探针进程。
  可以用 `node scripts/test-asr.js data/audio/<某个片段>.m4a 2400` 单独确认服务只是慢而不是坏了。
- **转录超时（`fetch failed` / `Headers Timeout Error`）**：Node 的 `fetch`（undici）对响应头有
  约 300 秒的硬上限，ASR 单段处理超过 5 分钟就会被它掐断，报 `fetch failed`（cause 为
  `Headers Timeout Error`），并不是服务挂了。现在 ASR 与 LLM 请求都走 `src/util.js` 里的
  `httpPost()`（内置 `http` 模块，无 headers 超时），单段允许 40 分钟，并自动重试 3 次；
  若一段仍然失败且它本身超过 5 分钟，会自动退化为更短的子片段逐个转写。局域网偶发 `EHOSTUNREACH`
   （ASR 机器满载时网络栈短暂不可达）靠重试即可恢复；已完成的片段有缓存，重试不会重新转写。
- 片段长度改变后旧的 ASR 缓存不会被误用：缓存文件名带片段时长（`segNN_<时长>s.json`），
  切分方式变了就重新转写。
